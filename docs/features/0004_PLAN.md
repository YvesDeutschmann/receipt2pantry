# Feature Plan: One-day pool, meal slot control, Spoonacular quota

Meal planner is out of MVP. Testers get one cook picker, not a week of meals. Stop generating a 7-day pool, let the user pick breakfast/lunch/dinner (so they can plan dinner on a lunch break), and meter `complexSearch` the same way as `findByIngredients` / recipe details so a hot generator stops at partial instead of eating the vendor quota. Set `SPOONACULAR_CALL_BUDGET` to a tester-sized number for prod (tens per hour, not 500). Put a hard daily cap on the Spoonacular dashboard (launch-readiness already called that a five-minute must-do).

Do not change cache TTLs. Do not re-enable the meal planner. No schema migration.

## Locked decisions

- Planning window is **one day**. Delete the `range(7)` loop. Intra-day simulated depletion stays only when one request asks for more than one meal type.
- Slot control is a **Recipes session override**, defaulting to local hour (05–10 breakfast, 11–15 lunch, else dinner). It does **not** write `household.suggestion_meal_slots` (that flag is still “does this household eat this meal”).
- The picker **filters** to the selected slot. Off-slot cards stay in the pool but are not shown.
- Generate calls send `meal_types: [selectedSlot]`. Onboarding, receipt-scan, and Settings refresh send the device’s current preferred slot. Empty/low selected slot refills that slot only.
- `clear_unused` is scoped to the meal types in that run. A dinner regen must not wipe unused breakfast/lunch rows.
- Count `complexSearch` on cache miss: budget check, then `_record_external_call("complexSearch")`, then `requests.get`. Budget/quota mid-run still marks the generation `partial` and does not `clear_unused`.
- Code + Fly default `SPOONACULAR_CALL_BUDGET` is **30** per worker per 3600s (2 gunicorn workers ≈ 60/hour). Period unchanged.
- Vendor daily cap is an operator step in the Spoonacular dashboard, documented in the deploy runbook. Not an application table.

## Current state

`PoolGenerator.generate_pool` walks 7 days × household meal types (default breakfast+lunch+dinner) and calls `RecipeService.search_recipes_complex` with `number=5`, `fillIngredients`, and `addRecipeInformation`. That is up to 21 vendor calls per regen. `search_recipes_complex` uses the 1-hour `_complex_cache` but is **explicitly unmetered**: `test_static_complex_search_has_no_budget_hook` and `test_recipe_complex_search_not_counted` pin that `_call_count` stays 0.

`SPOONACULAR_CALL_BUDGET` defaults to 500 in `backend/config.py` and 250 in `fly.toml` (comment: 2 workers ≈ 500/hour). `get_call_stats` is unused in routes. `/health` does not expose it.

`GET /suggestions` is pool-first and returns all unused meal types mixed into shelves. `frontend/src/pages/Recipes.jsx` ranks with `flattenCookDeck` / `preferredMealTypeForHour` using a frozen local hour; title follows the hour; there is no slot toggle. Low-watermark refill fires if **any** slot depth is `< 2`, then generates the full household slot list. `api.suggestions.triggerGeneration` already accepts `mealTypes` but almost no caller passes it.

`PoolStoreService.clear_unused(household_id, meal_type=None)` already supports a meal-type filter. The generator calls it unfiltered on `completed`.

## Phase 1 — Quota monitoring

Bound `complexSearch` and shrink the tester budget before changing how much pool is generated.

### Files

- `backend/services/recipe_service.py` — `search_recipes_complex`, `_record_external_call`, `is_budget_exceeded`
- `backend/config.py` — `SPOONACULAR_CALL_BUDGET` default
- `fly.toml` — `[env] SPOONACULAR_CALL_BUDGET`
- `docs/runbooks/deploy.md` — env table + Spoonacular dashboard cap
- `docs/implementation_briefs/mvp_gaps/06-launch-readiness-findings.md` — finding 3.7 / hard-blocker 11 spend caps
- `tests/services/test_suggestion_cost_caching.py`
- `tests/services/test_recipe_service.py` (only if complexSearch cache/budget cases live there)

### Algorithm (`search_recipes_complex`)

1. Build the existing cache key (household, user, ingredients, number, ranking, ignore_pantry, meal_type).
2. If `_complex_cache` hit within TTL, return it. Do not record a call. Do not check budget.
3. If `is_budget_exceeded()`, raise `AIServiceException` with message `Spoonacular call budget exceeded for this period`. Do not `requests.get`.
4. `_record_external_call("complexSearch")` (JSON log `event=spoonacular_external_call`, no API key / user / ingredients).
5. `requests.get` complexSearch as today. On 402/429 raise `RecipeQuotaException` via `_raise_for_spoonacular_http`.

`get_recipes_by_pantry` and `get_recipe_details` stay as they are. `PoolGenerator` already maps `AIServiceException` and `RecipeQuotaException` from `_recipes_for_step` to `final_status="partial"` and skips `clear_unused`. After Phase 2, a budget miss on the single slot is one failed call and the previous unused rows for that slot remain.

### Budget values

- `Config.SPOONACULAR_CALL_BUDGET` default `"30"` (env still overrides).
- `SPOONACULAR_CALL_BUDGET_PERIOD_SECONDS` stays `3600`.
- `fly.toml` `SPOONACULAR_CALL_BUDGET = '30'`.
- Deploy runbook: replace the `250` / “≈ 500/hour” row with 30 per worker, 2 workers ≈ 60/hour, tester-sized.

### Spoonacular dashboard (operator, not code)

In `docs/runbooks/deploy.md` add a short “Spoonacular spend cap” subsection:

- Log into the Spoonacular API console for the production key.
- Confirm the plan’s daily point allotment and set the tightest available hard cap / billing alert (launch-readiness finding 3.7: hard spend caps on the Spoonacular dashboard, five-minute must-do).
- Record the chosen daily point cap and the key’s last-four in the runbook (not the key itself).
- Note that in-app budget is per Flask worker and does not replace the vendor cap; 402 remains the hard stop.

Update `06-launch-readiness-findings.md` item 3.7 / blocker 11 to point at that runbook step. Do not add a `spoonacular_call_telemetry` table or a `/health` stats field in this feature.

### Tests (Phase 1)

- Replace `test_static_complex_search_has_no_budget_hook` with an assertion that `search_recipes_complex` calls `is_budget_exceeded` and `_record_external_call` before `requests.get`.
- Replace `test_recipe_complex_search_not_counted` with: cache miss increments `_call_count` and logs `endpoint=complexSearch`; cache hit does not.
- Budget exceeded: `requests.get` not called; `AIServiceException` raised.
- Extend `test_static_budget_before_every_instrumented_get` instrumented set to include `search_recipes_complex`.
- Config default test: `SPOONACULAR_CALL_BUDGET == 30`; env override test unchanged in spirit.

## Phase 2 — Drop the week fetch

Generate today only, and only the meal types the caller asked for.

### Files

- `backend/services/pool_generator.py` — `generate_pool`
- `backend/routes/pool.py` — `generate_pool` (quota HTTP mapping)
- `backend/services/pool_store_service.py` — only if `clear_unused` needs a multi-type helper; filter already exists
- `tests/services/test_pool_generator.py`
- `tests/backend/test_routes/test_pool.py`
- `docs/implementation_briefs/suggestion-pool.md` and `t1-05-pool-generator.md` only if they still claim a 7-day window (correct in passing; do not rewrite those briefs)

### Algorithm (`generate_pool`)

1. Mutex via `start_generation` unchanged (`already_running` short-circuit, no clear).
2. Snapshot pantry once. Load banned + swiped ids once.
3. For each `meal_type` in `meal_types` **once** (no day loop): `_recipes_for_step` → accumulate rows (still cap 5, still skip banned/swiped/run_ids). On `AIServiceException` / `RecipeQuotaException`, set `partial`, stop further meal types.
4. After a non-empty candidate set, deplete the simulated pantry from the top candidate (inline `extendedIngredients` preferred; else `get_recipe_details`, which is already budgeted). Depletion exceptions are warned and swallowed except `RecipeQuotaException`.
5. If `final_status == "completed"`: for each requested meal type, `clear_unused(household_id, meal_type=that)`, then `add_suggestions` for the accumulated rows. Never call unfiltered `clear_unused(household_id)`.
6. `complete_generation` as today.

Route: if the generator returns `partial` or `failed` with `suggestions_generated == 0` and the error is quota/budget (`RecipeQuotaException` or the budget-exceeded `AIServiceException` message), respond 429 `{ code: "recipe_quota" }` with the existing copy “Daily recipe quota reached, try again later.” so testers see the same banner as live suggestion 429s. Non-empty completed runs stay 200. `already_running` stays 200.

When `meal_types` is omitted, keep today’s household-slot fallback — still one day, so a legacy caller costs at most 3 `complexSearch`es, not 21.

### Tests (Phase 2)

- Happy path: `search_recipes_complex` called once per requested meal type; not 7×.
- Two meal types in one request: second call sees depleted simulated pantry; `clear_unused` called once per those types with the filter, never unfiltered.
- Quota/budget on first slot: `partial`, `clear_unused` not called, `add_suggestions` not called.
- Route: zero-insert quota → 429 `recipe_quota`; completed → 200.
- Remove or stop using `@patch(..., range, return_value=[0])` once the day loop is gone.
- Existing mutex / no-clear-on-partial / threshold-walk / staple-fallback tests still pass.

## Phase 3 — Slot control

User can pick breakfast, lunch, or dinner. Local time is the default, not the only option.

### Files

- `frontend/src/utils/dinnerPickerRank.js` — filter + title-by-slot
- `frontend/src/utils/__tests__/dinnerPickerRank.test.js`
- `frontend/src/pages/Recipes.jsx` — selected slot, generate args, watermark, empty-slot refill
- New small control (e.g. `frontend/src/components/MealSlotControl.jsx`) using existing MISE/button styles; `PageHeader` already has `actions` if that is the cleanest mount
- `frontend/src/pages/onboarding/StaplesTemplate.jsx` — `fireSuggestionPoolWarmup`
- `frontend/src/pages/Settings.jsx` — refresh suggestions
- Receipt/onboarding triggers: `useAppSyncScheduler.js`, `useSafewaySync.js`, `useCostcoSync.js`, `SafewayConnectCard.jsx`, `CostcoOneTapSync.jsx`
- `frontend/src/tests/SuggestionScreen.test.jsx` and the triggerGeneration tests for Settings / Staples / sync hooks
- `frontend/src/tests/apiClient.test.js` only if the mealTypes body assertion is missing

### Algorithm (picker)

1. `selectedSlot` initializes to `sessionStorage` key `meald.selectedMealSlot` if it is breakfast|lunch|dinner, else `preferredMealTypeForHour(local hour)`.
2. After household load, if `suggestion_meal_slots[selectedSlot]` is false, snap to the preferred enabled slot, else the first enabled slot. Hide/disable toggles for slots the household turned off.
3. Segmented control: Breakfast / Lunch / Dinner. Changing it writes `sessionStorage`, resets deck index, does not call `PUT /households`.
4. `flattenCookDeck` / visible window take an explicit `mealType`. Keep cards whose `meal_type` equals that slot; keep `meal_type == null` (live fallback). Do not show breakfast cards on the dinner slot.
5. Page title uses the selected slot (`What's for Lunch?` etc.), not the frozen hour, once the user (or default) has a slot.
6. `generateThenReload` always sends `mealTypes: [selectedSlot]`.
7. Low-watermark: `getDepth` then refill only if `depth[selectedSlot] < 2`. Do not refill because some other slot is low.
8. After load/slot change, if the filtered deck is empty, generate that slot (same generate helper). On 429 / `recipe_quota`, set the existing quota error string and **do not** retry generation in that session until the user pulls to refresh.
9. Pull-to-refresh and empty-state refresh generate the selected slot only.

### Algorithm (non-Recipes triggers)

All `triggerGeneration` call sites pass `mealTypes: [preferredMealTypeForHour(new Date().getHours())]`. Share that helper from `dinnerPickerRank.js`. Do not pass all three types.

### Tests (Phase 3)

- Rank/flatten: explicit dinner slot omits breakfast/lunch rows; null `meal_type` remains.
- Title helper for slot, not only hour.
- Recipes: default slot follows hour; clicking Lunch sends `mealTypes: ['lunch']`; watermark uses only that slot’s depth; full other slots + empty selected slot still generates.
- 429 from generate does not loop generate.
- Onboarding warmup and receipt_scan (`items_added > 3`) pass a single current-slot `mealTypes` array.
- Settings refresh passes a single current-slot array.

## Out of scope

- Cache TTL changes (`_cache_ttl`, `_details_cache_ttl`, `_complex_cache`, `SUGGESTION_CACHE_TTL_SECONDS`)
- Meal planner UI / `FEATURE_MEAL_PLANNER`
- Persisting the picker slot on the household
- Exposing `get_call_stats` on `/health`
- Persistent `spoonacular_call_telemetry` table
- Changing `number=5` per slot or staple-fallback rules
- Backend `GET /suggestions?meal_type=` (client filter is enough)

## Implementation order

Phase 1 (quota + dashboard runbook) → Phase 2 (one-day generator + per-slot clear) → Phase 3 (slot control). 1 can ship alone and already protects testers. 3 depends on 2 so a slot switch cannot wipe the other slots’ unused rows.
