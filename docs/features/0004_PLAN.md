# Feature Plan: One-day pool, meal slot control, Spoonacular quota

Meal planner is out of MVP. Testers get one cook picker, not a week of meals. Stop generating a 7-day pool, let the user pick breakfast/lunch/dinner (so they can plan dinner on a lunch break), and meter `complexSearch` the same way as `findByIngredients` / recipe details so a hot generator stops at partial instead of eating the vendor quota. Set `SPOONACULAR_CALL_BUDGET` to a tester-sized number for prod (tens per hour, not 500). Put a hard daily cap on the Spoonacular dashboard (launch-readiness already called that a five-minute must-do).

Do not change cache TTLs. Do not re-enable the meal planner. No schema migration.

## Locked decisions

- Planning window is **one day**. Delete the `range(7)` loop. Intra-day simulated depletion stays only when one request asks for more than one meal type.
- Slot control is a **Recipes session override** keyed by signed-in user, defaulting to local hour (05–10 breakfast, 11–15 lunch, else dinner). It does **not** write `household.suggestion_meal_slots` (that flag is still “does this household eat this meal”).
- The picker **filters** to the selected slot. Off-slot cards stay in the pool but are not shown. `suggestion_pool` is unique on `(household_id, recipe_id)`, so a dinner insert cannot reuse a breakfast unused/swiped id.
- Generate calls send `meal_types: [selectedSlot]` only from **explicit** refresh (PTR, empty-state Fill, cook/skip watermark) and from **one** initial-load auto-fill of the snapped slot. Changing the slot control never POSTs. Onboarding, receipt-scan, and Settings refresh send the device’s current preferred slot (not the Recipes session override), still one slot.
- Replace unused rows **per meal type that actually inserted ≥1 row**. Never `clear_unused(household_id)` unfiltered. Never clear a type that inserted 0. Persist types that have inserts even when the run later goes `partial`.
- Count `complexSearch` on cache miss: budget check, then `_record_external_call("complexSearch")`, then `requests.get`. Do not refund a recorded call on timeout/4xx/5xx.
- Code + Fly default `SPOONACULAR_CALL_BUDGET` is **30** per worker per 3600s (2 gunicorn **sync** workers ≈ 60/hour). Period unchanged. This is not a cluster-wide limiter.
- Vendor daily cap is an operator step in the Spoonacular dashboard, documented in the deploy runbook. Not an application table. Do not write the API key or any key fragment into git.
- In-app hourly budget and vendor 402/429 are **different 429s**. Budget must not use `code: "recipe_quota"` or daily/tomorrow copy. Cook plan does not raise `SPOONACULAR_CALL_BUDGET`.

## Reliability locks (from review)

These are contract, not commentary.

1. **Empty search must not wipe the slot.** `final_status == "completed"` with zero insertable rows (no candidates, all banned/swiped/already-pooled) still must not `clear_unused` for that type. Clearing then inserting 0 leaves an empty deck; the picker auto-refill will POST generate again and burn quota.
2. **Clear is gated on insert count, not candidate count.** `add_suggestions` skips ids already in the household pool (any status, any meal type). Five dinner candidates that already sit on breakfast insert 0. Treat that as “nothing to replace”: skip `clear_unused` for dinner.
3. **Replace order is clear-then-add, and only when the insertable set is non-empty.** New rows are `status=unused`, so a post-insert `clear_unused` would delete them. Per type: if that type has ≥1 `recipe_id` not already in the household pool, `clear_unused(household_id, meal_type=that)` then `add_suggestions` for those rows. If `add_suggestions` throws after clear, the slot can still go empty (existing non-atomic window; no RPC/transaction in this feature). Never enter that window when the insertable set is empty.
4. **Partial with rows still persists those types.** Quota/budget in `_recipes_for_step` stops further meal types (`partial`). Types already accumulated with an insertable set still replace. Types not yet fetched are not cleared. Depletion-path `RecipeQuotaException` / budget `AIServiceException` does **not** discard already-fetched candidates: swallow, stop further types, persist what you have. Only `_recipes_for_step` failure with zero insertable rows for a type leaves that type untouched.
5. **Skip already-pooled ids in the generator, not only in `add_suggestions`.** Load unused recipe ids for the household (all meal types) alongside banned + swiped into `_filter_recipes` / `run_ids`. Otherwise `number=5` is spent on uninsertable dupes and dinner stays empty while breakfast holds the matches. Do not raise `number` (out of scope).
6. **Requested `meal_types` intersect household enabled slots.** Body `["dinner"]` while `suggestion_meal_slots.dinner` is false must not call Spoonacular. Drop disabled types; if none remain, existing 400 “At least one of breakfast, lunch, dinner must be selected”. Omitted `meal_types` already uses household slots.
7. **In-app budget is per gunicorn sync worker, in memory.** Restart resets the counter (burst 30/worker). Two workers ≈ 60/hour. Do not add Redis, a DB counter, or `/health` stats. The dashboard cap is the hard stop. Record **before** `requests.get` so a retry storm still hits the local ceiling even when the vendor timed out.
8. **`start_generation` TOCTOU stays.** Select-then-insert can double-run under two workers. Do not add a unique partial index or RPC in this feature. Dual `complexSearch` is accepted; vendor cap is the backstop. `already_running` still short-circuits when the row is visible. Stale `in_progress` remains the existing 10-minute fail.
9. **Client auto-generate cannot loop.** Empty deck, 200 with 0 inserts, 5xx, `recipe_budget`, and `recipe_quota` are terminal for **automatic** refill of that slot until pull-to-refresh or the empty-state Fill button. `already_running` is wait-only (poll current slot; do not chain another POST from that call). Only `code === "recipe_quota"` sets `quotaBlockedRef` and the daily banner. **Do not** treat HTTP 429 alone as daily quota (`status === 429` without reading `code` re-creates the APK lie).
10. **In-flight generate is not “this slot is filled,” and slot switch is not a generate.** One in-flight POST at a time (server mutex is household-wide). Waiters for a different slot are not satisfied by that result. After it settles, **do not** POST for the slot the user merely switched to. Off-slot fill is PTR / empty-state Fill only.
11. **Session slot is per user, not per device.** Storage key `meald.selectedMealSlot:${userId}`. Do not use a global `meald.selectedMealSlot` (login B inherits A’s lunch). Snap-to-enabled overwrites that key. Logout/user change without a stored value falls back to hour. Still no `PUT /households`.
12. **Do not log pantry ingredient names, API keys, or user ids** on the `complexSearch` / `_record_external_call` path. Count + `meal_type` + endpoint is enough. Do not put Spoonacular key last-four in the runbook.
13. **Slot change is filter-only.** Tapping Lunch must not `POST /suggestions/pool/generate`. That tap was the APK trust bug: breakfast filled, lunch empty, silent generate, daily-quota banner. Empty off-slot uses the empty state (filtered deck length 0) plus explicit Fill / PTR.
14. **Split pool-generate 429s.** Zero-insert vendor `RecipeQuotaException` (402/429) → 429 `{ code: "recipe_quota", error: "Daily recipe quota reached, try again later." }`. Zero-insert in-app budget (exact `Spoonacular call budget exceeded for this period`) → 429 `{ code: "recipe_budget" }` with copy that does **not** say daily or tomorrow (e.g. “Recipe lookup limit reached for now. Try again in a bit.”). Inserts > 0 stay 200. Do not add a `RecipeBudgetException` type. Do not collapse both through `_is_quota_or_budget_error` → `recipe_quota`.
15. **Banners do not leak across slots.** `error` is page-global today. `recipe_budget` / empty-fill failures must not paint breakfast when the user switches back: clear non-`recipe_quota` errors on slot change. `recipe_quota` may stay (vendor day is over). `quotaBlockedRef` is vendor-only; it must not be set on `recipe_budget`.
16. **Empty CTA is the filtered deck, not `hasAnySuggestions`.** Breakfast unused rows in the payload make a mixed-shelf `hasRecipes` true while lunch flatten is empty. Gating the empty state on any-slot cards hides Fill lunch and forces either a blank deck or a silent POST. Empty state when `flattenCookDeck(payload, selectedSlot).length === 0`.
17. **No auto-POST until household slots have snapped.** The `[userId, householdId]` load effect runs once with `householdId == null` and whatever `sessionStorage` slot was stored (often yesterday’s lunch). That POST is not a user tap. Skip auto-generate until `fetchHousehold` has applied enabled slots (or failed). Then at most one auto-fill of the **snapped** slot if that filtered deck is empty.
18. **Do not fill all enabled slots on Settings/warmup/PTR.** One slot per call remains the quota reason for this feature. Empty lunch after a morning breakfast refresh is acceptable; a Lunch tap must not lie about a daily cap.

Residual (accepted, not a task): worker crash leaves `in_progress` up to 10 minutes; clear-then-add crash window when insertable set was non-empty; background warmup uses device hour, not Recipes session slot; explicit PTR after vendor 402 may retry and 429 again.

## Current state

`PoolGenerator.generate_pool` walks 7 days × household meal types (default breakfast+lunch+dinner) and calls `RecipeService.search_recipes_complex` with `number=5`, `fillIngredients`, and `addRecipeInformation`. That is up to 21 vendor calls per regen. `search_recipes_complex` uses the 1-hour `_complex_cache` but is **explicitly unmetered**: `test_static_complex_search_has_no_budget_hook` and `test_recipe_complex_search_not_counted` pin that `_call_count` stays 0.

`SPOONACULAR_CALL_BUDGET` defaults to 500 in `backend/config.py` and 250 in `fly.toml` (comment: 2 workers ≈ 500/hour). `get_call_stats` is unused in routes. `/health` does not expose it.

`GET /suggestions` is pool-first and returns all unused meal types mixed into shelves. `frontend/src/pages/Recipes.jsx` ranks with `flattenCookDeck` / `preferredMealTypeForHour` using a frozen local hour; title follows the hour; there is no slot toggle. Low-watermark refill fires if **any** slot depth is `< 2`, then generates the full household slot list. `api.suggestions.triggerGeneration` already accepts `mealTypes` but almost no caller passes it.

`PoolStoreService.clear_unused(household_id, meal_type=None)` already supports a meal-type filter. The generator calls it unfiltered on `completed`. `add_suggestions` already skips swiped and already-present `(household_id, recipe_id)` rows.

### Lunch-quota trust bug (APK, motivates locks 13–18)

Morning refresh / Settings sends `mealTypes: [breakfast]` only. Lunch pool stays empty. Tapping **Lunch** runs `maybeRefillSelectedSlot` on the `selectedSlot` effect → silent `POST /suggestions/pool/generate` with `mealTypes: ['lunch']`. That 429 is shown as **“Daily recipe quota reached”** even when the failure is the in-app **30/worker/hour** budget (`pool.py` maps budget through `_is_quota_or_budget_error` → `recipe_quota`). `Recipes.jsx` treats **any HTTP 429** as daily quota (`status === 429 || code === recipe_quota`), sets page-global `error` + `quotaBlockedRef`, and blocks other slots. Cook plan does not raise `SPOONACULAR_CALL_BUDGET`. Empty state is gated on `hasAnySuggestions` (any slot), so lunch can show neither cards nor Fill when breakfast rows exist.

### Algorithm (`search_recipes_complex`)

## Phase 2 — Drop the week fetch

Generate today only, and only the meal types the caller asked for.

### Files

- `backend/services/pool_generator.py` — `generate_pool`
- `backend/routes/pool.py` — `generate_pool` (split `recipe_quota` / `recipe_budget` mapping + household-slot intersect); add `RECIPE_BUDGET_MESSAGE` alongside `RECIPE_QUOTA_MESSAGE` from `recipes.py`; remove or narrow `_is_quota_or_budget_error` so budget never maps to `recipe_quota`
- `backend/services/pool_store_service.py` — only if a helper to list unused recipe ids is cleaner than `get_pool`; filter on `clear_unused` already exists
- `tests/services/test_pool_generator.py`
- `tests/backend/test_routes/test_pool.py`
- `docs/implementation_briefs/suggestion-pool.md` and `t1-05-pool-generator.md` only if they still claim a 7-day window (correct in passing; do not rewrite those briefs)

### Algorithm (`generate_pool`)

1. Mutex via `start_generation` unchanged (`already_running` short-circuit, no clear, no vendor call).
2. Snapshot pantry once. Load banned + swiped + **unused pool recipe ids (all meal types)** once.
3. For each `meal_type` in `meal_types` **once** (no day loop): `_recipes_for_step` → accumulate rows (still cap 5, skip banned/swiped/unused-pooled/run_ids). On `AIServiceException` / `RecipeQuotaException` from `_recipes_for_step`, set `partial`, stop further meal types; do not drop rows already accumulated for earlier types.
4. After a non-empty candidate set, deplete the simulated pantry from the top candidate (inline `extendedIngredients` preferred; else `get_recipe_details`, already budgeted). Depletion `RecipeQuotaException` and budget `AIServiceException`: log, set `partial`, stop further types, **keep accumulated rows**. Other depletion exceptions: warn and continue.
5. Replace **per meal type**, not as a global “completed ⇒ clear all requested types”:
   - Build `insertable` = accumulated rows for that type whose `recipe_id` is not already in the household pool.
   - If `insertable` is empty: do not `clear_unused` for that type.
   - Else: `clear_unused(household_id, meal_type=that)` then `add_suggestions` for **that type’s** insertable rows.
   - Never call unfiltered `clear_unused(household_id)`.
   - Do this for insertable types even when `final_status == "partial"`. Skip all replaces on unexpected `failed` (exception before/during persist).
6. `complete_generation` as today. `suggestions_generated` is the sum of inserts, not candidate list length.

Route:

- Intersect body `meal_types` with household `suggestion_meal_slots` (same drop-disabled behavior as the omitted-body fallback). Empty after intersect → 400.
- If `suggestions_generated == 0` and `status` is `partial` or `failed`:
  - Vendor quota/rate (`RecipeQuotaException` messages: daily quota exceeded / rate limit exceeded) → 429 `{ code: "recipe_quota" }` + “Daily recipe quota reached, try again later.”
  - In-app budget (exact `Spoonacular call budget exceeded for this period`) → 429 `{ code: "recipe_budget" }` + non-daily copy (lock 14).
  - Do not use one `_is_quota_or_budget_error` bucket that maps both to `recipe_quota`.
- Partial/completed with inserts → 200. `already_running` → 200.

When `meal_types` is omitted, keep today’s household-slot fallback — still one day, so a legacy caller costs at most 3 `complexSearch`es, not 21.

### Tests (Phase 2)

- Happy path: `search_recipes_complex` called once per requested meal type; not 7×.
- Two meal types both insertable: second call sees depleted simulated pantry; `clear_unused` called once per **those** types with the filter, never unfiltered.
- Two meal types, second returns 0 insertable: `clear_unused` not called for the empty type; first type still replaced.
- Completed with zero insertable rows: `clear_unused` not called, `add_suggestions` not called.
- Candidates already present on another slot: `clear_unused` not called for the requested type.
- Quota/budget on first slot: `partial`, no clear, no add.
- Quota/budget on second slot after first accumulated insertable rows: `partial`, first type replaced, second type not cleared.
- Depletion budget/quota: rows from that step still persisted; not treated as “zero-insert wipe.”
- Route: zero-insert vendor quota → 429 `recipe_quota` + daily copy; zero-insert budget → 429 `recipe_budget` + non-daily copy (not `recipe_quota`); completed with inserts → 200; body `meal_types: ['dinner']` with dinner disabled → 400 and generator not called. Update `test_post_generate_returns_429_on_zero_insert_quota_budget` to the budget code/copy.
- Remove or stop using `@patch(..., range, return_value=[0])` once the day loop is gone.
- Existing mutex / threshold-walk / staple-fallback tests still pass. Replace “no clear on any partial” with the per-type insertable rule above.

## Phase 3 — Slot control

User can pick breakfast, lunch, or dinner. Local time is the default, not the only option.

### Files

- `frontend/src/utils/dinnerPickerRank.js` — filter + title-by-slot
- `frontend/src/utils/__tests__/dinnerPickerRank.test.js`
- `frontend/src/pages/Recipes.jsx` — selected slot, generate args, watermark, empty-state Fill, in-flight, no generate on slot change, code-not-status 429 handling
- New small control (e.g. `frontend/src/components/MealSlotControl.jsx`) using existing MISE/button styles; `PageHeader` already has `actions` if that is the cleanest mount. Do not add a slot store/context.
- `frontend/src/pages/onboarding/StaplesTemplate.jsx` — `fireSuggestionPoolWarmup`
- `frontend/src/pages/Settings.jsx` — refresh suggestions
- Receipt/onboarding triggers: `useAppSyncScheduler.js`, `useSafewaySync.js`, `useCostcoSync.js`, `SafewayConnectCard.jsx`, `CostcoOneTapSync.jsx`
- `frontend/src/tests/SuggestionScreen.test.jsx` and the triggerGeneration tests for Settings / Staples / sync hooks
- `frontend/src/tests/apiClient.test.js` only if the mealTypes body assertion is missing

### Algorithm (picker)

1. `selectedSlot` initializes to `sessionStorage` key `meald.selectedMealSlot:${userId}` if it is breakfast|lunch|dinner, else `preferredMealTypeForHour(local hour)`. No userId → hour default, do not write a device-global key.
2. After household load, if `suggestion_meal_slots[selectedSlot]` is false, snap to the preferred enabled slot, else the first enabled slot, and write the snapped value to that user key. Hide toggles for slots the household turned off.
3. Segmented control: Breakfast / Lunch / Dinner. Changing it writes the user key, resets deck index, does not call `PUT /households`, **does not POST generate**, and clears non-`recipe_quota` page errors (lock 15).
4. `flattenCookDeck` / visible window take an explicit `mealType`. Keep cards whose `meal_type` equals that slot; keep `meal_type == null` (live fallback). Do not show breakfast cards on the dinner slot.
5. Page title uses the selected slot (`What's for Lunch?` etc.), not the frozen hour, once the user (or default) has a slot.
6. `generateThenReload` always sends `mealTypes: [selectedSlot]` captured at POST time. One in-flight generate per Recipes mount. Waiters for a **different** slot are not satisfied by that result (lock 10). On generate failure: set `quotaBlockedRef` and daily banner **only** when `err.response?.data?.code === 'recipe_quota'`. `recipe_budget` shows the API error string (non-daily); do not set `quotaBlockedRef`. Do not branch on `status === 429` alone (lock 9). `loadSuggestions` GET path: same rule if a live suggestion call ever 429s.
7. Remove the `useEffect` on `[selectedSlot]` that calls `maybeRefillSelectedSlot` — slot change is filter-only (lock 13). Keep initial-load auto-fill on the household-ready path only (lock 17).
8. Low-watermark after skip/cook: `getDepth` then refill only if `depth[selectedSlot] < 2`. Do not refill because some other slot is low. Cook/skip watermark is user-driven and is not blocked by the auto-refill attempted set.
9. **Do not auto-generate on slot change.** After household snap (lock 17), if the **snapped** slot’s filtered deck is empty, auto-generate that slot **once** (mark attempted **before** the POST). Not for a stored slot seen before snap. Not when the user later taps Lunch. Terminal for that auto-fill: 200/0, 5xx, `recipe_budget`, `recipe_quota`. `already_running`: poll current slot only; do not chain another POST from that call (lock 10).
10. Pull-to-refresh and empty-state **Fill** (shown when filtered deck length is 0, lock 16) clear `quotaBlockedRef` + auto-refill attempted for the selected slot, then generate the selected slot only. PTR after `recipe_quota` is an explicit retry, not an auto-loop. Render empty state when `flattened.length === 0`, not `!hasAnySuggestions`.

### Algorithm (non-Recipes triggers)

All `triggerGeneration` call sites pass `mealTypes: [preferredMealTypeForHour(new Date().getHours())]`. Share that helper from `dinnerPickerRank.js`. Do not pass all three types. Do not read Recipes `sessionStorage` (background warmup stays hour-based).

### Tests (Phase 3)

- Rank/flatten: explicit dinner slot omits breakfast/lunch rows; null `meal_type` remains.
- Title helper for slot, not only hour.
- Recipes: default slot follows hour; **clicking Lunch does not call `triggerGeneration`**; empty lunch with breakfast cards in the payload still shows the lunch empty state (Fill); Fill / PTR send `mealTypes: ['lunch']`; watermark after skip/cook uses only that slot’s depth.
- Load with `householdId == null` does not POST generate. After household snap, empty snapped slot may auto-generate once.
- `recipe_quota` 429 shows daily copy and sets `quotaBlockedRef`. `recipe_budget` 429 does not show daily copy, does not set `quotaBlockedRef`, and does not remain on screen after switching back to a slot that has cards. HTTP 429 without `recipe_quota` must not take the daily path.
- 200 completed with 0 cards / 5xx / either 429 code do not loop **automatic** generate.
- Slot switch during in-flight: does not POST the new slot when the first generate settles. No `useEffect([selectedSlot])` refill.
- Session key is per `userId`; a second user does not inherit the first user’s slot from a global key.

- Settings refresh passes a single current-slot array.

## Implementation order

Phase 1 (quota + dashboard runbook + Cook-key check) → Phase 2 (one-day generator + per-type insertable replace + split `recipe_quota` / `recipe_budget`) → Phase 3 (slot control: filter-only switch, vendor-only daily banner). 1 can ship alone and already protects testers. 3 depends on 2 so a slot switch cannot wipe the other slots’ unused rows, and so empty regen cannot wipe the selected slot.
