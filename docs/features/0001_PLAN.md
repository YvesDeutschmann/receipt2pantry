# Feature Plan: Foundation Architecture for Meald

## Description
Establish a minimal but production-ready foundation for Meald's backend, frontend, and data layers. Create a clean, modular codebase that can scale easily as new features (portal logins, receipt parsing, recipes) are introduced. This foundation will provide clear separation of concerns, security best practices, and a structured pathway for adding new grocery providers.

## Current State Analysis

### Existing Components
- **my_safeway_login.py**: Monolithic Safeway automation script with embedded browser control, login flow, and order fetching
- **parsers/safeway_parser.py**: Receipt parser that extracts structured data from Safeway email receipts
- **pyproject.toml**: Basic dependency management with Playwright, dotenv, click, rich

### Missing Components
- Flask backend with route/service separation
- React frontend with Tailwind CSS
- Supabase database integration
- API layer for frontend-backend communication
- Configuration management system
- Migration system for database schema
- Proper secrets management (AWS Secrets Manager integration)
- Logging and error handling infrastructure
- Testing framework setup

#### 1.5 Provider Abstraction Layer

**Files to create:**

- `backend/providers/safeway_provider.py`: Refactor existing `my_safeway_login.py` into this structure
- `backend/providers/provider_registry.py`: Registry pattern for provider discovery

**Base provider interface:**
```python
class BaseProvider(ABC):
    @abstractmethod
    def login(self, credentials: Dict) -> bool
    
    @abstractmethod
    def fetch_receipts(self, since: datetime) -> List[Dict]
    
    @abstractmethod
    def handle_mfa(self, mfa_code: str) -> bool
    
    @property
    @abstractmethod
    def provider_name(self) -> str
```

**Refactoring strategy for SafewayProvider:**
1. Extract browser management into separate concerns
2. Convert class methods to use dependency injection (pass browser context as parameter)
3. Remove direct file I/O and screenshot logic (move to utils)
4. Return structured data instead of boolean success flags
5. Implement error handling with custom exceptions
6. Remove `main()` function and CLI interaction

### Phase 2: Database Schema

#### 2.1 Initial Schema Design

**File to create:**
- `migrations/001_initial_schema.sql`: Initial database schema

**Tables to define:**

1. **users**: User account information (use Supabase Auth, reference only)
2. **grocery_accounts**: Links users to grocery providers
   - `id` (uuid, primary key)
   - `user_id` (uuid, foreign key to Supabase auth.users)
   - `provider` (text, e.g., 'safeway', 'qfc', 'costco')
   - `username` (text, the email/username for the grocery account)
   - `vault_key_id` (text, reference to AWS Secrets Manager secret ID)
   - `is_active` (boolean)
   - `mfa_required` (boolean)
   - `last_successful_login` (timestamp)
   - `created_at` (timestamp)
   - `updated_at` (timestamp)

3. **receipts**: Parsed receipt metadata
   - `id` (uuid, primary key)
   - `user_id` (uuid, foreign key)
   - `grocery_account_id` (uuid, foreign key)
   - `provider` (text)
   - `order_id` (text, provider's order identifier)
   - `order_date` (date)
   - `total_amount` (decimal)
   - `num_items` (integer)
   - `raw_data` (jsonb, full receipt data)
   - `fetched_at` (timestamp)
   - `created_at` (timestamp)

4. **receipt_items**: Individual items from receipts
   - `id` (uuid, primary key)
   - `receipt_id` (uuid, foreign key)
   - `name` (text)
   - `category` (text)
   - `price` (decimal)
   - `quantity` (integer)
   - `regular_price` (decimal, nullable)
   - `savings` (decimal, nullable)
   - `created_at` (timestamp)

5. **automation_logs**: Logs of automation runs
   - `id` (uuid, primary key)
   - `user_id` (uuid, foreign key)
   - `grocery_account_id` (uuid, foreign key)
   - `status` (text: 'success', 'failure', 'mfa_required')
   - `error_message` (text, nullable)
   - `receipts_fetched` (integer)
   - `started_at` (timestamp)
   - `completed_at` (timestamp)

**Indexes:**
- `grocery_accounts(user_id, provider)`
- `receipts(user_id, order_date)`
- `receipts(order_id)` (unique)
- `receipt_items(receipt_id)`
- `automation_logs(user_id, started_at)`

**Row-level security (RLS):**
- Enable RLS on all tables
- Users can only access their own data
- Service role can access all data for automation

## Algorithms and Patterns

### Provider Plugin System

The provider system uses a registry pattern to enable dynamic loading:

1. **Registration**: Each provider registers itself in `provider_registry.py`
2. **Discovery**: The registry maps provider names (e.g., 'safeway') to provider classes
3. **Instantiation**: Services request providers by name from the registry
4. **Execution**: Providers implement common interface but have provider-specific logic

**Algorithm:**
```
1. Load provider registry on application startup
2. For each provider in registry:
   a. Verify provider implements BaseProvider interface
   b. Register provider name -> class mapping
3. When receipt fetch requested:
   a. Retrieve provider from registry by name
   b. Instantiate provider with configuration
   c. Execute provider.login() then provider.fetch_receipts()
   d. Pass results to parser
   e. Store parsed results via supabase_service
```

### Error Handling Flow

All service functions follow consistent error handling:

1. **Try-Catch**: Wrap external calls in try-catch blocks
2. **Custom Exceptions**: Raise domain-specific exceptions
3. **Logging**: Log errors with context (user_id, provider, operation)
4. **Response**: Return structured error response with status code
5. **Propagation**: Let Flask error handlers convert exceptions to HTTP responses

**Example:**
```python
try:
    credentials = secrets_service.retrieve_user_credentials(user_id, provider)
except SecretsNotFoundException:
    logger.error(f"Credentials not found for user {user_id}, provider {provider}")
    raise AuthenticationException("Provider credentials not configured")
except Exception as e:
    logger.error(f"Unexpected error: {e}")
    raise DatabaseException("Failed to retrieve credentials")
```

## Implementation Notes

### Dependency Injection Pattern
All services should accept their dependencies as function parameters rather than importing them:

```python
# Good
def fetch_receipts(user_id: str, provider: str, supabase_client, secrets_client):
    ...

# Bad
from backend.services.supabase_service import client
def fetch_receipts(user_id: str, provider: str):
    client.query(...)
```

### Pure Functions
Services should be stateless and return values rather than mutating global state:

```python
# Good
def parse_receipt(email_content: str) -> Dict:
    items = extract_items(email_content)
    return {"items": items, "total": sum(i["price"] for i in items)}

# Bad
parsed_items = []
def parse_receipt(email_content: str):
    global parsed_items
    parsed_items = extract_items(email_content)
```

### Configuration Over Convention
Use explicit configuration rather than magic values:

```python
# Good
config = Config()
timeout = config.PLAYWRIGHT_TIMEOUT

# Bad
timeout = 30000  # hardcoded
```
