# Feature Plan: Multi-Factor Authentication (MFA) Support for Provider Login

## Description

When a user connects their Safeway account, the login process may require multi-factor authentication (MFA). Currently, the automation halts at this point with no way for the user to respond. This feature introduces a flow where the backend can pause login, notify the frontend that MFA is needed, and resume once the user provides their MFA code. The goal is to deliver a seamless, interactive experience where the user can enter their MFA code directly in the UI without restarting the entire login flow.

## Current State Analysis

### Existing Infrastructure
- **`MFARequiredException`** already defined in `backend/utils/exceptions.py`
- **`handle_mfa(mfa_code: str)`** method stubbed in `BaseProvider` interface and `SafewayProvider`
- **`mfa_required` field** already exists in `grocery_accounts` table (boolean)
- **`automation_logs.status`** supports `'mfa_required'` value
- **Provider routes** exist at `backend/routes/providers.py` but don't handle MFA flows
- **Frontend provider page** at `frontend/src/pages/Providers.jsx` has no MFA handling

### Gaps to Address
- No MFA detection logic in `SafewayProvider._perform_login()`
- No mechanism to suspend/resume browser sessions during MFA wait
- No API endpoints for checking MFA status or submitting MFA codes
- No session management for tracking pending login attempts
- No frontend UI for MFA code input
- No timeout/cleanup for abandoned MFA sessions
- No real-time status updates from backend to frontend

#### 1.2 MFA Detection in SafewayProvider

**File to modify:**
- `backend/providers/safeway_provider.py`

**Changes to `_perform_login()` method:**

After clicking the final sign-in button (line 173), add MFA detection logic:

1. **Wait for page transition** with multiple possible selectors:
   - Success: Account name selector appears (`a#auth_signin_link span[data-qa='hdr-accnt-nm']`)
   - MFA Required: MFA input field appears (e.g., `input#code`, `input[name="verificationCode"]`)
   - Error: Error message appears

2. **Detect MFA prompt** by checking for common MFA UI elements:
   - Input fields with names like `code`, `verificationCode`, `mfaCode`, `otpCode`
        <input type="text" aria-label="Enter Verification Code" placeholder="------" maxlength="6" size="6" min="6" max="6" formcontrolname="otpCode" aria-describedby="error-otp" required="" class="input-field__otp-code ng-untouched ng-pristine ng-invalid" data-dashlane-rid="6e0de0b5120b5479" data-dashlane-classification="otp,part" data-kwimpalastatus="alive" data-kwimpalaid="1760648117910-7">
   - Text containing "verification code", "authentication code", "enter code", "6-digit code"
        <h2 class="auth-styles__title">We noticed you’re signing in from a new device</h2>
   - Form elements with MFA-related aria-labels

3. **Raise `MFARequiredException`** with context:
   - Include session identifier
   - Capture screenshot for debugging
   - Extract MFA instructions text from page if available

**Example detection code:**
```python
# After clicking sign in (line 173)
try:
    # Wait for either success or MFA prompt
    self.page.wait_for_timeout(2000)
    
    # Check for MFA input field
    mfa_input = self.page.locator("input[name*='code'], input[id*='code'], input[placeholder*='code']").first
    if mfa_input.count() > 0:
        # MFA is required
        raise MFARequiredException("MFA verification required to complete login")
    
    # Otherwise wait for successful login indicator
    self.page.wait_for_selector("a#auth_signin_link span[data-qa='hdr-accnt-nm']", timeout=10000)
except TimeoutError:
    # Check if MFA appeared during timeout
    mfa_input = self.page.locator("input[name*='code'], input[id*='code']").first
    if mfa_input.count() > 0:
        raise MFARequiredException("MFA verification required")
    raise
```

## Algorithms and Patterns

### MFA Login Flow Algorithm

**Step-by-step process:**

1. **User initiates login:**
   - Frontend: User clicks "Test Connection" on provider card
   - Frontend: Opens credentials modal
   - User enters username and password
   - Frontend: Calls `POST /providers/safeway/test`

2. **Backend processes initial login:**
   - Backend: Creates provider instance
   - Backend: Calls `provider.login(credentials)`
   - Provider: Starts browser, navigates to Safeway
   - Provider: Fills username and password
   - Provider: Submits login form

3. **MFA detection:**
   - Provider: Waits for page response
   - Provider: Detects MFA input field on page
   - Provider: Raises `MFARequiredException`
   - Route handler: Catches exception
   - Route handler: Creates login session with browser context
   - Route handler: Returns 202 with session_id

4. **Frontend handles MFA requirement:**
   - Frontend: Receives 202 response
   - Frontend: Stores session_id
   - Frontend: Opens MFA dialog
   - Frontend: Starts polling session status

5. **User provides MFA code:**
   - User: Enters 6-digit code in dialog
   - Frontend: Calls `POST /providers/safeway/login/{session_id}/mfa`
   - Backend: Retrieves session
   - Backend: Calls `provider.handle_mfa(code)`
   - Provider: Fills code into MFA input
   - Provider: Submits MFA form
   - Provider: Waits for verification

6. **MFA verification:**
   - **If successful:**
     - Provider: Verifies login success
     - Provider: Saves session to file
     - Backend: Updates session state to `completed`
     - Backend: Cleans up browser
     - Backend: Returns 200 success
     - Frontend: Shows success message
     - Frontend: Closes dialog
     - Frontend: Refreshes provider status
   
   - **If failed:**
     - Provider: Detects error message
     - Provider: Raises `AuthenticationException`
     - Backend: Returns 400 with error
     - Frontend: Displays error in dialog
     - User: Can retry with different code

7. **Session expiration:**
   - Background worker: Checks for expired sessions
   - Worker: Terminates browser contexts
   - Worker: Updates database to `expired`
   - Frontend polling: Detects expired state
   - Frontend: Closes dialog with timeout message

### Session State Machine

**States:**
- `pending_mfa`: Login initiated, waiting for MFA detection
- `awaiting_code`: MFA detected, waiting for user to provide code
- `completed`: MFA verification successful, login complete
- `failed`: MFA verification failed or invalid code
- `expired`: Session timed out before completion

**Transitions:**
- `pending_mfa` → `awaiting_code`: MFA prompt detected
- `awaiting_code` → `completed`: MFA code verified successfully
- `awaiting_code` → `failed`: MFA code verification failed
- `awaiting_code` → `expired`: Session timeout reached
- `failed` → `awaiting_code`: User retries with new code (optional)
- Any state → `expired`: Timeout or explicit cancellation

## Error Handling

**Common error scenarios:**

1. **Session not found:**
   - HTTP 404
   - Message: "Login session not found or expired"
   - Action: User must restart login

2. **Session expired:**
   - HTTP 410 Gone
   - Message: "Login session has expired"
   - Action: User must restart login

3. **Invalid MFA code:**
   - HTTP 400
   - Message: "Invalid verification code"
   - Action: User can retry (up to max attempts)

4. **MFA verification timeout:**
   - HTTP 408
   - Message: "MFA verification timed out"
   - Action: User must restart login

5. **Browser context lost:**
   - HTTP 500
   - Message: "Login session interrupted"
   - Action: User must restart login

## Security Considerations

1. **Session security:**
   - Session IDs are UUIDs (non-guessable)
   - Sessions tied to user_id (RLS enforced)
   - Sessions expire after timeout
   - Browser contexts isolated per session

2. **MFA code handling:**
   - Never log MFA codes
   - Clear codes from memory after use
   - Implement rate limiting (future enhancement)
   - Limit retry attempts

3. **Browser context isolation:**
   - Each session has dedicated browser context
   - No sharing of cookies/storage between users
   - Proper cleanup prevents memory leaks
