# === TECH STACK AND PACKAGE MANAGEMENT ===
- tech stack: UV, Python, Flask, React, Supabase, Playwright
- use `uv add` when installing new packages (never pip or npm directly)
- prefer lightweight, composable dependencies; avoid large all-in-one frameworks

# === CODE STYLE AND ARCHITECTURE ===
- prefer pure functions that take explicit parameters and return values
- avoid keeping state in global variables; pass data explicitly
- compose steps as a sequence of functions rather than using class hierarchies
- all Flask routes go in `/routes/` and should call pure service functions from `/services/`
- add structured logging to every major operation
- prefer dependency injection through function parameters rather than globals

# === ENVIRONMENT AND CONFIGURATION ===
- you cannot see or modify `.env` files directly  
  → tell the user exactly what environment variables to add when needed
- load environment variables using `python-dotenv`
- do not hardcode secrets or API keys
- the environment is mangaged using UV; always use "uv add ..." to add new libraries to the project

# Deployment Context
- this is a cloud-hosted web application
- the backend (Flask) will be containerized and deployed to a managed service (e.g. AWS, Render, or Supabase Edge Functions)
- environment variables and credentials will be provided through a secret manager
- local dev uses `.env` but production uses secret injection

# === Security & Secrets Policy ===
security:
  secrets_handling:
    - GrocerySync never stores plaintext or reversible user credentials in Supabase or Postgres.
    - Grocery account credentials (usernames, passwords, or MFA tokens) must be stored securely using:
        1. Supabase Vault for early-stage dev/testing
        2. AWS Secrets Manager (or GCP Secret Manager / Azure Key Vault) for production deployments
    - The database (`grocery_accounts` table) only stores metadata (provider, username reference, vault key ID).
    - Encrypted or hashed credentials should never be persisted in Supabase tables.
    - The `encryption_service` must only handle short-lived tokens for in-memory automation sessions.
    - Never commit `.env` files or any secrets into version control.
    - All environment variables must come from cloud-managed secret managers in deployment environments.

# === Cloud Context ===
architecture:
  deployment_target: "Cloud (AWS preferred)"
  guidelines:
    - Treat Supabase as the authentication + data persistence layer, not a secrets manager.
    - All secret rotation, MFA tokens, and encryption keys belong in AWS Secrets Manager.
    - Local development may use Supabase Vault only for temporary testing.
    - Ensure all configurations use `Config` or environment variables, not hard-coded values.

# === DATABASE AND SCHEMA CHANGES ===
- when data schema changes are required, write the SQL statements to a `.sql` file under `/migrations/`
  → the user will apply them manually

# === APP EXECUTION ===
- do not try to start or run the app (`flask run`, `npm start`, etc.)
  → the app runs in a separate terminal managed by the user

# === FRONTEND ===
- prefer React functional components with hooks (no class components)
- use Tailwind CSS for layout and styling
- backend API calls should be made via a centralized `apiClient.js`

# === GENERAL GUIDELINES ===
- write clear, production-level code that can run without manual patching
- use descriptive commit messages and document new endpoints or functions
- keep each feature self-contained and traceable to a user story or phase
- ust a test-driven development approach
- test new code throughly with unit tests; make sure to cover edge cases
- a feature is only considered finished when all unit tests pass
