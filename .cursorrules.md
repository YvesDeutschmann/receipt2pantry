## 🛠 Tech Stack & Workflow
- **Package Management:** Use `uv add` for Python and `npm install` for Frontend. Do not use `pip`.
- **Architecture:** Follow the Controller-Service pattern. Flask routes in `/routes/` handle orchestration; all domain/business logic must reside in pure, testable functions in `/services/`.
- **Source of Truth:** Refer to `/supabase/migrations/` for the authoritative schema. Do not hallucinate columns.

## 🛡️ Data Integrity Standards
- **Strict Comparison:** Use explicit `is not None` checks for numeric or database values (especially when `0` is a valid state). Avoid broad truthy/falsy checks.
- **Identification:** Use UUIDs or normalized keys for entity resolution. Never use partial string matching (`in`, `LIKE`, `.contains`) for logic unless explicitly building a "search" feature.
- **Atomicity:** Operations affecting multiple tables must be wrapped in a transaction or use a database RPC (PostgreSQL function) to ensure consistency.
- **Time-Determinism:** Functions involving date/time logic must accept an optional `today` or `reference_date` parameter for deterministic unit testing.

## 🏗️ Phase-Driven Implementation Protocol
- **Context Isolation:** Prioritize logic defined in the specific attached `@brief` or `@plan`. Do not implement multiple phases simultaneously.
- **Test-First Mandate:** Before implementation, scaffold the corresponding unit tests (`pytest` or `vitest`) to define success criteria.
- **Pre-Flight Check:** Check existing patterns in `apiClient.js` and service modules to ensure new code remains consistent with the existing stack.

## 📝 General Coding Style
- **Explicit over Implicit:** Prefer verbose, clear logic over "clever" one-liners.
- **Functional Core:** Keep logic "pure" (data in -> data out). Push side effects (DB/API calls) to the boundaries of the service layer.
- **Type Safety:** Use Pydantic models for backend validation and PropTypes or interface-like structures for frontend components.
- **Test-First Mandate** You are required to scaffold unit tests (pytest for backend, vitest for frontend) before writing implementation logic.
- **Self-Audit:** Upon completion, generate a "Logic Audit" report comparing the implementation against the specific constraints of the sub-task brief.
- **Atomic Transactions** Multi-table operations (e.g., soft-deleting a pantry item and inserting into history) must use the PostgreSQL RPCs
- **Exact Matching** When resolving ingredients or pantry items, never use substring matching (e.g., in or .contains()). You must use exact ID or normalized name matching to prevent "rice" matching "rice vinegar"
## 🧱 Micro-Brief Orchestration (The "1-Brief-1-Build" Rule)
- **Constraint:** Composer is forbidden from implementing a "Master Plan" directly.
- **Dependency:** Every "Build" session must be preceded by a "Micro-Brief" generated by an Architect model (Opus).
- **Format:** Micro-Briefs must follow the 4-part structure:
    1. **Technical Contract:** (API signatures, Component props, Schema references).
    2. **Logic Guardrails:** (Specific edge cases, e.g., "Raw Meat" put-back rules).
    3. **Test-First Suite:** (Defined list of pytest/vitest cases).
    4. **Definition of Done:** (Specific functional outcomes to verify).
- **Scope Limit:** If a Micro-Brief exceeds 5 logic-heavy tasks or involves more than 3 distinct files, it must be split further into sub-phases (e.g., Phase 4.1a, 4.1b).
